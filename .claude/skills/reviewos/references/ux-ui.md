# ReviewOS Module：UX / UI

涵蓋：UX / UI / Interaction / Information Architecture / Motion / Brand / Design System。
核心提問：

> 使用者此刻想完成什麼？介面幫了忙還是擋了路？

所有發現轉為 Core 的 Issue 格式輸出。禁止喜好式評論——每個視覺問題必須翻譯成使用者後果。

## 審查前先建立使用脈絡

1. 這個畫面的主要任務是什麼？（一個畫面只能有一個主要任務）
2. 使用者是誰、使用頻率？（每天用 50 次的後台 vs 一生用一次的註冊頁，密度標準相反：高頻工具要密、低頻流程要淺）
3. 進入此畫面前使用者知道什麼、帶著什麼預期？

## UX Review

- **任務路徑**：完成主要任務需要幾步、幾次決策？每一步是否都在推進任務？
- **認知負荷**：使用者需要同時記住幾件事？需要記住上一頁的資訊才能操作這一頁 = Issue。
- **錯誤預防與復原**：破壞性操作有沒有確認或 undo？錯誤訊息是否告訴使用者「接下來怎麼辦」而不只是「錯了」？
- **空狀態與首次體驗**：新使用者打開是空白一片，還是有引導下一步？
- **等待體驗**：超過 1 秒的操作有沒有回饋？超過 10 秒有沒有進度？

## UI Review

視覺問題必須寫成因果句：「<視覺現象>，導致<使用者後果>」。

- **視覺層級**：閉眼再睜眼，第一眼落在哪？是否為主要任務的入口？視覺重點衝突（兩個以上元素搶第一眼）= Issue。
- **閱讀順序**：排版動線與任務順序是否一致？
- **色彩語言一致性**：同一顏色是否代表同一語義？（綠色又是成功又是主按鈕又是連結 = 語義稀釋）
- **Icon 辨識**：無 label 的 icon 是否可能被誤讀？非通用符號必須配文字。
- **密度與留白**：資訊分組是否靠留白／分隔清楚表達？相關的近、無關的遠。
- **文字**：行長、對比、層級數量（超過 3-4 級字階 = 層級系統失效）。

## Interaction Review

- 可點擊的東西看起來可點嗎？不可點的東西看起來不可點嗎？
- 觸控目標尺寸（行動裝置最小 44px）與誤觸距離。
- 狀態回饋：hover / pressed / disabled / loading 是否齊備？
- 手勢與慣例：是否違反平台慣例（返回行為、下拉更新）？違反慣例需要極強理由。

## Information Architecture Review

- 命名是使用者的語言還是內部術語？（「團購管理」vs「Campaign Entity」）
- 分類是否 MECE？一個項目可能被找的兩個地方是否都到得了？
- 導航深度：常用功能埋幾層？
- 搜尋／捷徑是否覆蓋高頻任務？

## Motion Review

- 動畫是否傳達了資訊（來源、去向、因果）還是純裝飾？
- 時長：介面動效 150-300ms 為常規；阻擋操作的動畫超過 500ms = Issue。
- 高頻操作的動畫會不會在第 50 次時變成折磨？
- 是否尊重 reduced-motion 設定？

## Brand / Design System Review

- 同一元件在不同頁面是否長得不一樣？（按鈕圓角、間距、色票漂移）
- 品牌個性是否只存在 Logo，而未反映在文案語氣、色彩、插圖風格？
- Design token 是否存在且被使用，或到處是 magic number？
- 例外元件（不符合系統的一次性設計）數量——例外太多代表系統已失效。

## 本模組常見 P0 判準

- 使用者無法完成主要任務（入口找不到、流程斷裂、按鈕失效於某平台）
- 破壞性操作無確認且不可復原
- 表單送出失敗且清空使用者輸入
- 關鍵資訊在主要裝置上不可讀（對比、字級、被遮擋）
