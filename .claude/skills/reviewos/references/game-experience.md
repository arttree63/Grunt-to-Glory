# ReviewOS Module：Game Experience Review

**角色：Lead Game Designer（首席遊戲設計師）**
核心提問：

> 玩家玩到這裡，心裡到底發生了什麼？

驗證「玩家感受正確」，不是「功能正確」。不評論架構（Software 的事）、不評論系統重疊（Game System 的事）、不評論介面排版（Game UI 的事）。所有發現轉為 Core 的 Issue 格式輸出。

## 前置：先過 Game System

新系統應先通過 `game-system.md` 的三道門再進本審查。系統無存在理由時，體驗審查是浪費。

## 五項體驗審查

### 1. Player Psychology（玩家心理）
- **玩家期待什麼？** 例：10F 玩家期待新玩法，不是 +10% 傷害。
- **玩家最想知道什麼？** 例：Boss 戰玩家想知道「我能不能贏」，不是 HP 剩多少。
- **玩家有沒有選擇？** 很多遊戲看起來很多按鈕，其實只有一條答案。直接抓出來。
- **玩家知道下一步嗎？** 每個時刻都應有一個明確的短期目標。

### 2. Decision（決策真偽）
- 假決策：攻擊+5% vs 攻擊+8% → 只是算數。
- 真決策：分身 vs 燃燒 vs 軍旗 → 不同玩法路線，無法比大小。
判準：兩個選項若能用計算機分出高下，就不是決策。

### 3. Reward & Feedback（獎勵與回饋）
- **值得嗎？** 獎勵強度與投入是否成比例？大投入小獎勵 = 背叛感。
- **玩家知道自己成功了嗎？** Perfect 夠不夠爽？Boss Break 夠不夠爽？成功時刻必須有明確、即時、與強度成比例的回饋。
- 獎勵的「爽」來自演出＋意義（改變 Build），不只是數字上升。

### 4. Core Loop & Pacing（核心循環與節奏）
- 核心循環一句話寫出來：<動作> → <回饋> → <成長> → 回到<動作>。寫不出來 = P0。
- 畫出流程時間軸，標記事件間距：

```
開始 → 教學 → Boss → 命運 → 職業 → 命運 → Boss
```

- 是不是一直打斷？一直沒事情？高潮太密？高潮太少？

### 5. Emotion Curve（情緒曲線）
每個事件用三欄標記法（光寫情緒名稱不夠，必須可驗證）：

| 事件 | 預期情緒 | 觸發條件 | 失敗徵兆 |
|---|---|---|---|
| 命運降臨 | 驚喜 | 選項中至少一個改變規則 | 玩家秒選最高數值 |
| 30F 職業 | 承諾 | 選擇後鎖定本輪路線 | 玩家感覺選哪個都一樣 |
| Boss | 緊張 | 勝負在戰前不確定 | 玩家掛機無視 |

目標曲線形狀：好奇 → 驚喜 → 爽 → 緊張 → 解放 → 期待下一輪。

## 固定檢查清單

- □ 第一分鐘有沒有期待？
- □ 十分鐘後還有沒有期待？
- □ 有沒有假選擇？
- □ 有沒有真正的 Build？
- □ 有沒有高潮？
- □ 有沒有低潮？（全程高潮 = 沒有高潮）
- □ 玩家知道下一步嗎？
- □ 玩家有故事可以分享嗎？（「我那輪抽到雙分身」= 有故事；「我打到 87F」= 只有數字）

## Retention（留存視角）

- 本輪結束的瞬間，玩家想的是「再來一輪」還是「終於結束了」？
- 跨輪鉤子：下一輪有什麼**這一輪決定的**新東西？（傳承展示、解鎖預告）
- 回訪理由是「想玩」還是「怕損失」（每日簽到焦慮）？後者短期有效、長期折損品牌。

## 子領域補充

**Combat**：戰鬥核心循環幾秒？玩家在循環中的主動決策是什麼？若答案是「看著」，確認這是刻意的 idle 設計還是缺失。

**Level Design**：每個關卡／樓層是否提出一個「問題」？連續三關同一個問題 = 填充內容。

**Narrative**：敘事在玩法之上而非旁邊。切斷玩法的敘事（強制對話、不可跳過演出）以 Pacing 標準審查。
