# ReviewOS Module：Software

涵蓋：Software / Architecture / Performance / Frontend / Backend / Database / API / Security / Accessibility。
本模組驗證的是「系統正確且可持續」。核心提問：

> 六個月後接手的工程師（可能是你自己），會在哪裡受苦？

所有發現轉為 Core 的 Issue 格式輸出。Impact 欄位在本模組常見對象：工程、維護、使用者、商業。

## 審查前先建立技術脈絡

1. 產品目標與規模（10 個使用者的內部工具 vs 上千商家的 SaaS，標準完全不同）
2. 團隊規模與交接情境（一人專案的過度架構是負債，不是資產）
3. 生命週期階段（prototype 驗證期 vs 商業化營運期）

**依脈絡調整嚴格度。** 對 prototype 挑 SOLID 違規是雜訊；對營運中 SaaS 忽略資料一致性是失職。

## Top-Down 審查順序（由大到小，先抓大問題）

1. **邊界與資料流**：模組邊界在哪？資料在哪裡被改變？狀態的唯一真相來源（single source of truth）是否存在？
2. **失敗路徑**：外部服務掛掉、網路逾時、並發寫入、部分成功時，系統發生什麼事？（金流、通知、webhook 尤其必查重試與冪等性）
3. **核心流程正確性**：主要商業流程有沒有邏輯洞？
4. **可維護性**：命名、重複、耦合、測試覆蓋關鍵路徑。
5. **細節**：風格、微效能——多數屬 P2/P3。

## 子領域判準

**Architecture**
- 抽象層數是否與問題複雜度相稱？為未來需求預留的抽象若未來未到，就是現在的成本。
- 依賴方向：底層是否反向依賴高層？循環依賴？
- 每個服務／模組能否一句話說明職責？說不出來 = 邊界錯了。

**Frontend**
- 狀態放置位置：server state（快取層）與 client state（UI 狀態）是否混在一起？
- 重新渲染範圍與資料獲取瀑布（waterfall）。
- 錯誤與載入狀態：每個非同步操作三態（loading / error / empty）是否都有 UI？漏掉的那個就是使用者看到白畫面的地方。
- 表單：驗證時機、送出中防重複、失敗後資料是否保留。

**Backend / API**
- API 是否洩漏內部資料模型？（回傳整個 DB row 含敏感欄位）
- 冪等性：付款、建單、webhook 重送是否安全？
- 錯誤格式一致性、狀態碼語義正確性。
- 分頁、排序、過濾是否在資料層完成而非撈全表到記憶體。

**Database**
- N+1 查詢、缺索引的高頻查詢、無界限成長的表。
- 交易邊界：跨表更新是否原子？
- 軟刪除／稽核需求是否在 schema 層面考慮。

**Performance**
- 先問「慢在哪裡有證據嗎？」無量測的效能優化建議違反 Evidence Based，不得提出。
- 檢查數量級問題（O(n²)、全表掃描、迴圈內 I/O），不檢查微優化。

**Security**
- 輸入信任邊界：所有外部輸入（含 webhook、query string、上傳檔名）是否驗證？
- 授權檢查位置：是否只在 UI 層擋、API 層裸奔？（IDOR：改 ID 就能看別人資料）
- 秘密管理：金鑰是否進版控？
- 注意：本審查指出風險類型與位置，不產出攻擊利用細節。

**Accessibility**
- 鍵盤可達性：所有互動能否不用滑鼠完成？焦點順序與可見性。
- 語義標籤與 alt；顏色是否為唯一資訊載體；對比度。
- 動態內容：Modal 焦點陷阱、Toast 是否被輔助技術朗讀。

## 本模組常見 P0 判準

- 資料遺失或損毀路徑（無交易保護的多步驟寫入、無冪等的金流）
- 授權缺失（IDOR、未驗證的管理端點）
- 核心商業流程的邏輯錯誤
- 秘密洩漏（金鑰進版控、API 回傳敏感欄位）
